btc500.net automation — who does what, when, and what you must do

Two OpenCode agents on two launchd jobs, one shared git checkout, deterministic Node scripts that grade the agents so a model can never approve its own verdict, and one human action that only you can take.

06:00 · growth-cycle preflight → ship → gate → prove production serves it
→
09:30 · growth-review measure → verdict → mandates for tomorrow → asks for you
→

Nothing waits on a human to keep the machine running — your input only changes the results.

1 · The three actors

① 06:00 every day

growth-cycle

net.btc500.growth → scripts/autonomous/run-growth-cycle.sh
  1. script preflight.mjs — refresh the price archive, health-check the site, list due experiment readings, read the last review
  2. output preflight.json — the order of work: notes → mandates → backlog
  3. agent growth-cycle · GROWTH_PROMPT.md — 5 free models in order, each time-boxed; ships content, tools and fixes as commits
  4. gate npm test + tsc --noEmit — nothing is pushed without it
  5. verify push → wait for the Vercel status on that exact sha → check last-deploy.json against the live HTML → homepage + sitemap 200
  6. record status-history.csv · last-status.txt · the day's log · notification
Outcome
a commit proven to be what production serves — or an honest failure status.
Check
last-status.txt, YYYY-MM-DD.log, git log
You
only on a red status, or a mandate that says “prepare the asset”.
② 09:30 every day

growth-review

net.btc500.review → scripts/autonomous/run-review-cycle.sh · deep mode on Sundays
  1. sync wait for the growth cycle's lock — defer rather than collide
  2. measure fetch Search Console · GA4 · URL inspection
  3. script collect-results.mjs — signals + rule.mayClaimImproving + ask-effect
  4. agent growth-review · GROWTH_REVIEW.md — verdict, why, mandates, targets, owner_asks, self_changes
  5. gate validate-review.mjs — does the verdict obey the data? are the asks written when results are flat?
  6. hand over render-asks.mjs — owner-asks.txt + notification body + commit body
  7. valid review-history.csv · last-review.txt · review log · notification
    invalid / absent rejected verdict committed as evidence
Outcome
a verdict you can trust (improving, stagnant or failing), work ordered for tomorrow, one action ordered for you.
Check
last-review.txt, review-latest.json, the review log
You
read the verdict, then do the ask.
③ Whenever results are flat

You — the only actor who can distribute

the agents are denied posting, pitching and linking by policy
  1. read the ask: notification · ASKS: line in the commit · state/owner-asks.txt
  2. publish copy-paste and post — X @btc500halving, a community comment, a newsletter pitch, an awesome-list PR, an embed offer
  3. measured GA4 records the referral (x.com, github.com, the newsletter) → next 09:30 scores it in ask-effect
  4. otherwise step in on a red status: nothing mechanical can clear those
Outcome
referral sessions, indexation movement, non-brand clicks.
Check
owner-asks.txt, GA4 referrals, next review's verdict
You
five minutes per ask — it is the highest-leverage input in the system.
Hand-off ② → ① review-latest.json mandates are injected into tomorrow's preflight.json and outrank the backlog.
Hand-off ② → ③ owner_asks[] becomes owner-asks.txt, the notification and the commit's ASKS: lines.
Hand-off ③ → ② Your post becomes a referral session; the next review scores it green, flat (<7 days) or stalled.

4 · Where the automation needs you

Every stagnant / failing verdict An ask in owner-asks.txt: the post written out in full (≤280 chars + link), the account, the best time, and the metric that proves it worked. Due within 14 days — after 7 days with no referral it comes back as stalled and is restated narrower. → highest leverage: this is the only channel that brings strangers in
Any red status in the notification validation-failed · push-blocked · site-down · deploy-failed · no-commit (all 5 models exhausted) · dirty-tree. → nothing mechanical can clear these; the run stops and waits for you
Anything outside the repository Accounts, submissions, permissions, newsletters, communities — the agents are denied them by policy (no gh, no publishing, no force-push, secrets unread). → the reviewer turns these into mandates marked owner
ask-effect stalled twice Two reviews in a row with no session from the channel you were asked to work means the channel itself is wrong — pick a different audience. → the reviewer will say so explicitly and re-ask with a narrower action
